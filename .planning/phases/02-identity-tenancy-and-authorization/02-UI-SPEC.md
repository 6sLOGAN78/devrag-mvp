## Forms contract (applies to every form in this phase)

Layout:

- Single column. Field stack gap md (16px). Label above control, 4px gap; helper or error 4px below the control.
- Label: Label style, `htmlFor` bound by `FormLabel`. Required fields are the default and are not marked with asterisks; optional fields (none in this phase) would say "(optional)".
- Submit row: 24px below the last field. Auth forms: full-width primary button. Settings cards: right-aligned primary in the card footer (`CardFooter`, `justify-end`).
- Controls never rely on placeholder text for meaning. Placeholders are used only for email (`name@example.com`) and the OTP (`123456`), muted.

Validation:

- react-hook-form `mode: "onTouched"` (validate on first blur, then on each change); `reValidateMode: "onChange"`. On invalid submit, focus the first invalid field.
- zod messages are i18n keys (e.g. `errors.password.min`), translated by `FormMessage`. No raw English strings in schemas.
- Rules mirror the server and are shared constants: email must be a valid address (trimmed, lowercased on submit); nickname 1 to 64 characters after trim; password 8 to 128 characters, length only, no composition rule (D-02, D-29); OTP exactly 6 digits.
- Inline error text: `text-xs font-normal` in `--destructive`, with a 16px `CircleAlert` icon, id referenced by `aria-describedby`; control gets `aria-invalid="true"` and a destructive border. Meaning is never color-only.

Server errors:

- Request calls for auth forms use `silent: true` so the global toast does not duplicate the inline message. A form-level `Alert` (`role="alert"`) renders above the submit row with the server `message` exactly as returned, never augmented, only if it is a non-empty string up to 160 characters; otherwise the fallback copy. The login error is therefore always "Email or password is incorrect" (D-04).
- Credential failure on `/api/v1/auth/login` (HTTP 401 or envelope error) must NOT trigger the session-purge path, the "Session expired" toast, or a redirect. Only authenticated requests holding a stored token purge (existing `sentToken` guard).
- HTTP 429: the same `Alert` shows the server message; the submit button stays enabled.
- After a failed login the password field is cleared and focused; the email is kept.

Password visibility (`password-input`):

- Trailing icon button inside the control (`Eye` / `EyeOff`, 16px icon in a 40px target, `aria-pressed`, `aria-label` "Show password" / "Hide password"). Defaults to hidden. Toggling swaps `type` between `password` and `text` and keeps caret position and focus on the input. Resets to hidden on unmount and after a failed submit.
- `autocomplete`: login `username` (email) and `current-password`; register `email`, `nickname`, `new-password`; change password `current-password` then `new-password`; reset `new-password`; OTP `one-time-code` with `inputMode="numeric"`, `maxLength=6`. Passwords never enter the URL, query cache or logs.
- No confirm-password field anywhere (visibility toggle replaces it) (auto-selected, not user-reviewed).

States:

| State | Treatment |
|-------|-----------|
| Default | Border `--input` |
| Focus | 2px accent ring, 2px offset (inherited) |
| Invalid | Destructive border, inline error |
| Disabled | 50% opacity, `cursor-not-allowed`, not focusable |
| Read-only (email on profile) | `--muted` fill, normal-contrast text, focusable, `aria-readonly`, helper text explains why |
| Submitting | Submit button `aria-disabled="true"`, `aria-busy="true"`, inline 16px `Loader2` spinner, label unchanged, clicks ignored; fields stay as they are (no focus loss) |
| Dirty (settings forms) | "Save profile" is `aria-disabled` until the form is dirty and valid |

## Screen: Sign in and sign up (`/login`) — UI-06

Composition (BareLayout): wordmark, then one `Card` (`max-w-sm`, p-6) centered horizontally; vertically centered at heights >= 640px, else 64px from the top. Corner cluster holds language and theme.

Sign-in mode (default):

1. Card title (Heading): "Sign in to devRag"
2. Alert slot (server error)
3. Email field
4. Password field (label row: "Password" left, link "Forgot password?" right, goes to `/forgot-password`)
5. Primary button "Sign in", full width
6. Footer line (only when registration is enabled): "No account yet?" + link-button "Create one" (switches to `?mode=register`)

Sign-up mode (`?mode=register`, only when `GET /api/v1/system/config` reports `register_enabled=true`):

1. Title: "Create your account"
2. Alert slot
3. Nickname, Email, Password (helper: "At least 8 characters.")
4. Primary button "Create account"
5. Footer: "Already have an account?" + link-button "Sign in"

Behaviour:

- Mode is URL state (`?mode=register`); switching preserves `next`, clears the form and Alert, moves focus to the card title (`tabIndex=-1`).
- Registration disabled (D-01): the sign-up form and the "Create one" link are not rendered; a deep link to `?mode=register` shows sign-in with the caption "New accounts are turned off on this server." in muted Label style under the button. While the config request is loading or if it fails, treat registration as off and render no switch link (fail closed; sign-in always works).
- After successful registration the SPA signs in with the same credentials, then navigates. After login or registration: to `next` when it is a same-origin path (must start with a single `/`, not `//`, no scheme; otherwise `/home`), else `/home`.
- Already signed in and visiting `/login`: redirect to `/home` once session recovery succeeds.
- Duplicate email on register: show the server message in the Alert; do not clear fields.
- Token handling: Bearer token in `localStorage` (Claude's discretion in CONTEXT; unchanged).
- Focus on mount: the email field (sign-in) or nickname field (sign-up).

Test ids: `login-page`, `login-form`, `register-form`, `login-error`, `field-email`, `field-password`, `field-nickname`, `password-toggle`, `login-submit`, `register-submit`, `mode-switch`.

## Screen: Forgot password (`/forgot-password`) — UI-08 (assumed mapping for AUTH-16..18)

BareLayout, one `Card` (`max-w-sm`), three steps held in component state (not in the URL). A "Step {n} of 3" caption (Label, muted) sits above the step title. Focus moves to the step title on each step change. "Back to sign in" link-button at the bottom of every step.

| Step | Title | Fields | Primary button | Notes |
|------|-------|--------|----------------|-------|
| 1 | "Reset your password" | Email | "Send code" | Always advances to step 2 on any 2xx, never confirms an account exists (D-07). Body line above field: "Enter your account email. We'll send a 6-digit code." |
| 2 | "Enter the code" | Code (single input, mono 14px, `tracking` widened by letter-spacing only, no six-box widget) | "Verify code" | Body: "If an account exists for {email}, a 6-digit code is on its way. It expires in 10 minutes." Secondary link-button "Send a new code", disabled with a visible countdown "Send a new code in {seconds}s" for 60 seconds after each send (matches the 1 per 60 s limit); a new send replaces the old code (D-06) |
| 3 | "Choose a new password" | New password (helper "At least 8 characters.") | "Reset password" | Body note: "You'll be signed out on every device." |

Errors: wrong or expired code shows the server message in the Alert (fallback "That code is incorrect or has expired."); after the server invalidates the code (5 wrong attempts) the server message is shown and the user is returned to step 1 with the email kept. HTTP 429 on send shows the server message; the countdown restarts from the server `Retry-After` when present. On success: navigate to `/login` with success toast "Password reset" / "Sign in with your new password." No session is created by reset.

Test ids: `forgot-page`, `forgot-step-{1|2|3}`, `forgot-resend`, `field-code`.

## Auth guard and session recovery — UI-02, UI-04, UI-07

| Situation | Behaviour |
|-----------|-----------|
| No token, guarded route | `<Navigate to="/login?next={encoded path+search}" replace>`; no toast |
| Token present, boot or refresh | Fetch `GET /v1/user/info`; until it resolves render `SessionSkeleton` inside `BareLayout`: wordmark plus three `Skeleton` lines, shown only after 150ms, with a visually hidden `role="status"` text "Restoring your session". No flash of the signed-out UI, no flash of the shell |
| Recovery succeeds | Store user (id, nickname, email, avatar, language, tenant id, role) in the Zustand user store; render the route inside its layout; apply `user.language` if no explicit local choice differs |
| Recovery returns 401 (expired, revoked, signed out elsewhere, password changed elsewhere) | Purge token, store and query cache; navigate to `/login?next=...`; toast "Session expired" / "Sign in again to continue." (deduped, shown once). This replaces Phase 1 flag 3 now that `/login` exists |
| Recovery fails with network or 5xx | Do NOT purge the token. Render `ErrorState` in `BareLayout`: heading "Couldn't load your session", body per the standard error body, actions "Try again" (primary) and link "Sign in again" (to `/login`, which purges) |
| Any later request returns 401 with a sent token | Same purge and redirect as above, preserving the current path in `next`, no hard reload |
| Password change success on this device | Token is already invalid server-side (D-08): purge locally, navigate to `/login`, toast "Password changed" / "Sign in with your new password." No "Session expired" toast |

Public routes (never guarded): `/login`, `/forgot-password`, `*`.

## Screen: API tokens (`/user-setting/api`) — UI-35

Documented behaviour (D-12): full tokens are stored and listable, so there is NO "shown once" promise. The UI masks tokens by default and lets the owner reveal and copy them at any time. Copy must never say a token can't be viewed again.

`PageHeader` "API tokens"; action "Create token" (`Plus` icon, primary) rendered only when at least one token exists. Intro paragraph (Body, muted, max-w-prose): "Use an API token to call the devRag API from your own code. Send it as a Bearer token in the Authorization header."

List card (semantic table, wrapped in `overflow-x-auto`):

| Column | Content |
|--------|---------|
| Token | Mono 14px. Masked: first 7 characters (`ragflow-`'s `ragflow`) hidden by design, shown as `ragflow-••••••••` plus the last 4 characters; revealed shows the full value, `break-all`. Never truncated with an ellipsis |
| Created | Localized medium date (`Intl.DateTimeFormat`, current language) with `<time datetime>` |
| Actions | Three icon buttons, 8px gap: Show/Hide (`Eye`/`EyeOff`, `aria-pressed`), Copy (`Copy`, swaps to `Check` for 2s), Delete (`Trash2`) |

Icon button labels include the token tail for screen readers: "Show token ending {last4}", "Copy token ending {last4}", "Delete token ending {last4}". Copy writes the full token to the clipboard even while masked and shows toast "Token copied" (success, 4s). If the clipboard API is unavailable, reveal the token and show toast "Couldn't copy" / "Select the token and copy it manually."

Create flow: clicking "Create token" immediately calls the create endpoint (no options exist per docs), then opens a `Dialog`:

- Title: "API token created"
- Body: "Treat this token like a password. Anyone who has it can act as you in this workspace. You can view it again from this page."
- Read-only mono field with the full token (selectable) and an adjacent "Copy token" `outline` button.
- Footer: primary "Done". Close via Done, X, Esc or overlay; focus returns to the Create button; the new token appears at the top of the list, masked.

Delete flow: row trigger opens an `AlertDialog`:

- Title: "Delete API token?"
- Body: "The token ending {last4} stops working immediately, and anything using it will get an authentication error. This can't be undone."
- Buttons: "Keep token" (cancel, default focus) and "Delete token" (destructive). Success toast "Token deleted".

States:

## Interaction conventions added in this phase

- Destructive confirmations: always `AlertDialog`; default focus on the cancel button; title "{Verb} {noun}?"; body names the object, the consequence and, where true, irreversibility; dismiss label "Keep {noun}" or a clear verb ("Stay in workspace"), never "Cancel" or "OK"; confirm label "{Verb} {noun}"; destructive fill. Non-destructive confirmations (role change) use the same dialog with the primary button.
- After a dialog closes, focus returns to the control that opened it (Radix default); after row removal, focus moves to the table caption (`tabIndex=-1`).
- Mutations invalidate only the affected TanStack queries; lists update without a page reload. No optimistic updates for destructive or role changes.
- Row buttons that run a request show an inline `Loader2` and `aria-busy`.
- Toasts: success 4s, errors per Phase 1 rules; auth forms and invite form use inline `Alert` for their own errors (`silent: true`) and toasts only for success.
- Dates: `Intl.DateTimeFormat(i18n.language, { dateStyle: "medium" })`. Counts use i18next plurals (`_one`/`_other`; Chinese uses `_other` only).
- Document titles: "{Page} - devRag" ("Sign in - devRag", "Home - devRag", "Profile - devRag", "API tokens - devRag", "Team - devRag", "Reset password - devRag"); `<html lang>` follows the active language (`en`, `zh`).

## Accessibility and Quality Floor (additions)

- Every input has a visible label bound with `htmlFor`; helper and error ids referenced by `aria-describedby`; `aria-invalid` on errors.
- Form-level `Alert` uses `role="alert"` (announced once on insertion). Step changes in forgot password move focus to the step title.

- Contrast: all new text pairs use the inherited tokens (>= 4.5:1). Accent links on `--card`: light #0F766E on #F1F5F9 is about 5:1; dark #2DD4BF on #131A22 is above 9:1.

- `<html lang>` follows the active language; mixed-language endonyms carry their own `lang`.
- The SPA never renders the password or token in the URL, document title, or toasts. Token values appear only in the tokens table, the created dialog, and the clipboard.
